## Pipeline architecture (confirmed)

The PDF was generated server-side by `/Users/abhinavanand/Files/Lawie/scripts/export-pdf.ts` (Puppeteer + custom HTML renderer). It is NOT generated by the browser-side `apps/web/src/components/editor/exportUtils.ts`. The script:

1. Reads SSE-event log files (`*.response.json`) emitted by the live API
2. Parses the `template_sections` event into `RenderedSection[]`
3. Runs each section through a hand-rolled `markdownToHtml()` (only handles `**bold**` and `*italic*`)
4. Wraps in HTML with embedded CSS, sends to Puppeteer, prints A4 PDF

Bugs are split between three layers:
- **Export script** (`scripts/export-pdf.ts`): markdown coverage, watermark CSS
- **Court-rule / template configs**: `{current_year}` mismatch, prayer template double-PS
- **AI prompt** (`docs/templates/bail_anticipatory.json` `prompt_context`): hallucinated second caption + disclaimer in body, raw markdown emission

## Bug 1: Markdown bold renders as literal asterisks

**Root cause file + line:** `/Users/abhinavanand/Files/Lawie/scripts/export-pdf.ts:103-110` (`markdownToHtml`) and `/Users/abhinavanand/Files/Lawie/scripts/export-pdf.ts:95-101` (`escapeHtml`)

**Why it's broken:** The renderer's `markdownToHtml()` does call `.replace(/\*\*(.+?)\*\*/g, '<strong>$1</strong>')` AFTER `escapeHtml()`. So bold *should* render. Looking at the actual PDF output (`**Roshan Oraon**`, `**FIR No. 215/2025...**` literal in body text), the asterisks are surviving. The cause is that the AI output contains bold spans that wrap across `<br>` line breaks within a paragraph or contain newlines mid-token (`split('\n')` at line 129 splits each line independently, so a `**...**` that spans two lines via `\n` gets split into `**...` + `...**` and neither half matches the non-greedy regex `\*\*(.+?)\*\*`). The non-greedy regex also fails when a single line has unbalanced asterisks (which the AI emits liberally — e.g. mid-sentence `**28 years**, resident of **PP Compound...**`). Net result: most bold survives but quite a few don't, and the user sees a salt of raw asterisks.

Secondary issue: the renderer does NOT handle markdown horizontal rules (`---`), unordered lists (`-`), or block-level constructs at all (see Bug 5). It also runs `markdownToHtml` per-line, so a list item or heading AI emits using markdown will not be rendered.

**Proposed fix (design, not code):** Replace the hand-rolled `markdownToHtml` + `escapeHtml` pair with a vetted markdown library — `marked` (already lightweight), or `markdown-it`. Run it on the full section content (not per-line), then post-process to keep alignment classes. Drop the `\n → <br>` replacement and use proper paragraph splitting from the markdown parser. This also gives us italic, hr, lists, blockquotes for free.

**Risk / blast radius:** `marked` adds ~50KB. Output HTML structure changes (paragraphs become `<p>`, not custom `<p style=...>` wrappers). The per-section alignment + heading detection at lines 132-148 will need reworking — heading detection currently uses a brittle ALL-CAPS / startsWith heuristic; switching to markdown means the AI prompt and templates must standardise on `# H1` / `## H2` for headings. This in turn requires updating all 6 template JSON files (`docs/templates/*.json`) to use markdown headings. Tests in `scripts/__tests__/export-pdf.test.ts` will need updates.

**Estimated effort:** M (1–2 hr for the renderer change; another ~1 hr to standardise heading conventions across template configs and update tests)

## Bug 2: `{current_year}` placeholder unfilled in cause title

**Root cause file + line:** `/Users/abhinavanand/Files/Lawie/apps/drafting/src/config/court-rules/jharkhand_hc.json:16-26` (uses `{year}`) vs `/Users/abhinavanand/Files/Lawie/apps/drafting/src/services/template-engine.service.ts:484-487` (substitutes `{year}` only in `case_nomenclature`, not `{current_year}`)

**Why it's broken:** The court rule JSON uses the placeholder `{year}` (e.g. `"anticipatory_bail": "Cr. Misc. No. _____ of {year}"`). The engine at template-engine.service.ts:484 only does `.replace(/\{year\}/g, ctx.current_year)` for that value. Then `replacePlaceholders()` (line 537) walks the rendered template and substitutes any `{xxx}` from context — but it only looks up keys that exist in the context, otherwise replaces with `_____`. Critically, the founder's PDF shows `Cr. Misc. No. _____ of {current_year}` literally — meaning the cause-title source string contained `{current_year}`, not `{year}`. This indicates someone (probably an older draft of `jharkhand_hc.json` or a stale cached deployment) shipped with `{current_year}` instead of `{year}`. On disk today the file uses `{year}` correctly, but the deployed PDF must have been made when the file said `{current_year}` — OR there is a second nomenclature path that bypassed the `{year}→current_year` swap.

There's also a subtle bug at `replacePlaceholders` line 538-543: when an unknown placeholder is encountered, it's replaced with `_____`. But `{current_year}` IS in the context (line 403 sets `current_year: String(now.getFullYear())`). So if it survives to the final pass, it WOULD resolve. The fact that it didn't means the substitution pass for the cause_title section ran BEFORE `current_year` was put in context, OR the case-nomenclature lookup short-circuited.

Re-reading: in `buildPlaceholderContext` line 484, `ctx.case_nomenclature = rule.case_nomenclature[nomenKey].replace(/\{year\}/g, ctx.current_year)` — this is hard-coded to swap `{year}` only. If the source string used `{current_year}`, the regex misses it. Then `case_nomenclature` is set on context as a literal string still containing `{current_year}`. Then `replacePlaceholders` runs on the cause_title TEMPLATE, sees `{case_nomenclature}` and swaps it in WHOLE (does not recursively expand). So the `{current_year}` token never reaches the placeholder loop and stays raw.

**Proposed fix:** Two changes are needed. (1) Standardise the placeholder in court-rule JSONs to `{year}` (already done in jharkhand_hc.json, audit the other 12 court-rule files for consistency). (2) Make `replacePlaceholders` recursive (run a second pass) so any `{current_year}` or other system placeholder embedded in a resolved value gets caught. Limit recursion to 2 passes to avoid loops. Better long-term: change the case_nomenclature handling at template-engine.service.ts:484 to run through `replacePlaceholders(rule.case_nomenclature[nomenKey], ctx)` instead of a one-off `.replace`.

**Risk / blast radius:** Recursive substitution could double-substitute if a value resolves to something that contains another placeholder name by coincidence (low risk, all placeholders are explicit). Audit all court-rule JSONs to confirm `{year}` is uniform. Touching template-engine.service.ts affects every template render — needs unit tests.

**Estimated effort:** S (≤30 min — small core change + a 2-line test)

## Bug 3: Watermark "DRAFT — Lawie Free Tie" (truncated, on every page)

**Root cause file + line:** `/Users/abhinavanand/Files/Lawie/scripts/export-pdf.ts:174` (literal source string) and `/Users/abhinavanand/Files/Lawie/scripts/export-pdf.ts:236-246` (CSS sizing)

**Why it's broken:** Two issues stacked.

(a) The literal string at line 174 is `DRAFT — Lawie Free Tier` — correct. The PDF shows "Free Ti" because the diagonal rotated text at 60pt overflows the A4 page right edge and gets clipped. CSS uses `position: fixed; top: 50%; left: 50%; transform: translate(-50%,-50%) rotate(-45deg); font-size: 60pt; white-space: nowrap` — no width constraint, so the rotated bounding box exceeds the page width and Puppeteer crops at the page boundary.

(b) Founder policy: NO watermark on court output, even free tier. Code at line 174 toggles via `clean: boolean` flag (passed from `--clean` CLI arg). Default is `clean=false` which APPLIES the watermark. The founder ran the script without `--clean`, hence the watermark.

**Proposed fix:** Flip the default. Two-step design: (1) immediate — change the export script default so `clean = !args.includes('--watermark')` (i.e., opt-in watermark for testing only). (2) longer-term — the watermark concept itself should be retired from the export pipeline because the founder doesn't want any watermark on legal output. Remove the watermark CSS block entirely; if free-tier branding is needed for marketing, do it as a separate PDF page (not as an overlay on legal text). Per docs/CLAUDE.md and team policy, court output should never carry rendering artifacts that an opposing counsel could mock.

**Risk / blast radius:** Low — only affects `scripts/export-pdf.ts`. No production server code today calls the watermark path. If we keep the flag for future paid-tier signaling, the truncation also needs fixing (`max-width: 100%` on the watermark and shrinking to ~40pt).

**Estimated effort:** S (10 min to remove + retest 12 PDFs)

## Bug 4: Duplicate cause-title block ("IN THE COURT OF THE SESSIONS JUDGE, RANCHI...")

**Root cause file + line:** AI hallucination, prompt-side. `/Users/abhinavanand/Files/Lawie/docs/templates/bail_anticipatory.json:105` (`prompt_context` for body section) and `/Users/abhinavanand/Files/Lawie/apps/drafting/src/services/template-engine.service.ts:611-639` (system prompt)

**Why it's broken:** The AI body section prompt (system prompt at template-engine.service.ts:622) tells the model: "Do NOT generate cause title, prayer, verification, advocate block, or disclaimer — those are handled by the template engine." However, in this run the model still emitted a SECONDARY mini-caption: `**IN THE COURT OF THE SESSIONS JUDGE, RANCHI**` followed by `**ANTICIPATORY BAIL APPLICATION UNDER SECTION 482...**` and then `---` BEFORE paragraph 1. This is pure hallucination — there is no code path that injects this string. Worse, the AI guessed the WRONG forum (Sessions Judge instead of High Court), confirming the model is inventing a court header rather than reading from form data.

The hallucination is enabled by two prompt weaknesses: (1) the rule "Do NOT generate cause title..." is buried as item 6 of 7 in the system prompt; (2) the bail_anticipatory `prompt_context` (the user-facing instruction block) does NOT repeat the prohibition — it focuses on the substantive body content. With no negative reinforcement at the user-prompt level, the model defaults to its training pattern of emitting a full caption block.

**Proposed fix:** Add a positive instruction at the very start of the body `prompt_context` for every template: `"Generate ONLY numbered paragraphs (1., 2., 3., ...). Do NOT emit any heading, caption, court name, application title, separator (---), or labels above paragraph 1. Begin your response with '1.'"` — and add a stop-sequence-style guard in code that strips any markdown heading lines before the first numbered paragraph. Belt-and-suspenders. Same change applies to all 6 templates.

**Risk / blast radius:** Low risk on the prompt change. The post-process strip needs care: define "before first `^\d+\.` line" precisely so it doesn't eat valid content. Update tests for all 6 templates.

**Estimated effort:** M (1 hr — prompt edits across 6 JSONs + a new sanitiser in drafting service + tests)

## Bug 5: Markdown horizontal rule `---` and italic `*inter alia*` showing as raw markdown

**Root cause file + line:** Same as Bug 1 — `/Users/abhinavanand/Files/Lawie/scripts/export-pdf.ts:103-110`

**Why it's broken:** `markdownToHtml` at line 103-110 only handles `**bold**` and `*italic*`. It has NO rule for horizontal rule (`---`), and the italic regex `/\*(.+?)\*/g` runs AFTER bold. When the AI output contains `*inter alia*` adjacent to other punctuation, the non-greedy match can fail (e.g., if the line has a `*` elsewhere, the regex pairs them across the wrong span). The PDF shows `*inter alia*` rendered as raw italic markup, confirming the regex didn't match. The `---` line just survives untouched because there's no rule for it.

**Proposed fix:** Folded into Bug 1's marked/markdown-it migration — those libraries handle hr, italic, lists, and edge cases like asterisks adjacent to punctuation correctly.

**Risk / blast radius:** Same as Bug 1 (single root cause).

**Estimated effort:** Folded into Bug 1 (0 incremental cost)

## Bug 7: "PS PS Chanho" duplicate in prayer

**Root cause file + line:** `/Users/abhinavanand/Files/Lawie/docs/templates/bail_anticipatory.json:114` — prayer template hard-codes `PS {police_station}` as a prefix

**Why it's broken:** The prayer template string at line 114 contains `...PS {police_station}, under Section 482...`. The form field `police_station` must have been entered by the founder as `PS Chanho` (with the "PS" prefix included in the user input). The template prepends another `PS `, giving `PS PS Chanho`. This is a known prompt-side / template-side anti-pattern: a template that adds a label assumes the field value is bare. Same bug pattern likely exists in other templates that prefix `FIR No. {fir_number}` etc.

**Proposed fix:** Two viable options. (a) Strip the `PS ` prefix from the form field VALUE on input — sanitise `police_station` to remove leading "PS " or "P.S." in `validateFormData` at template-engine.service.ts:754 or in a new normaliser. (b) Drop the `PS ` prefix from the template at bail_anticipatory.json:114 and rely on the user to include it. (a) is safer because field values flow into multiple templates; one sanitiser fixes all.

Audit other templates and form fields for the same anti-pattern: e.g., `FIR No. {fir_number}` (does the form value already contain "FIR No."?), `Section {sections_charged}` (does the form value have "Section"?). Likely a small cluster of fields.

**Risk / blast radius:** Form-input normaliser is scoped — only affects values where the prefix is duplicated. Add a unit test for `police_station: "PS Chanho"` → context value `"Chanho"`. Risk: an advocate types a station name that legitimately starts with "PS" (a station literally named "PS-something") — collision is unlikely; document the normalisation in form helper text.

**Estimated effort:** S (≤30 min)
